# Handoff to Claude Code — ontology research, CA/TX/federal relative placement

Written by a Claude session (Cowork, cloud-based) that ran the regulatory research for this project's ontology, before Christopher moves the project into Claude Code / VSCode to actually build against it. This document exists so a fresh Claude Code session — one with no memory of the conversation that produced these files — can pick this up without re-deriving any of it, and so a human reviewer can see exactly how confident to be in each piece.

Read this before touching the JSON files it describes. Read `CLAUDE.md` and the existing `docs/git-workflow.md` in the repo as usual — this document supplements those, it doesn't replace them.

## What this project is, in one paragraph

A hackathon prototype (DNHacks, Health & Public Service track) that helps caseworkers assemble and verify interstate foster/adoption placement packets under the ICPC, for a California↔Texas relative-placement case specifically. The architecture is ontology-first: regulatory requirements, documents, and consistency rules are authored as cited, structured data; a deterministic engine (`graph.ts`) derives a dependency graph from that data for the dashboard; a separate engine (`consistency.ts`) checks uploaded documents against it. No LLM is allowed to decide whether a requirement is met — only to extract facts from documents. Every requirement and document carries a `source_citation` and a `verified: false/true` flag; nothing invented is allowed to render as if it were confirmed.

## Methodology — how this data was actually produced

This is the part a fresh session most needs, because it determines how much to trust each entry.

**Tools used:** web search and a page-fetching tool that retrieves a URL and has a model summarize/answer questions about its content (not a raw-text dump — this matters, see limitation below), plus parallel sub-agent research tasks for the larger jobs (reading the full Texas and California regulatory documents).

**A real tool limitation, discovered and worked around, not hidden:** the fetch tool reliably retrieves roughly the first third to half of a very large PDF (tested on a 99-page California directives document) and becomes unreliable past that — on one specific question, five separate attempts at the same PDF gave contradictory answers, including flat "yes" vs "no." When this happened, the response was to say so explicitly rather than pick a plausible-sounding answer, and then find a different, better source instead of retrying the same failing method. That different source — the actual California statute (Welfare and Institutions Code) and codified regulation (Title 22 CCR), both published as short individual web pages instead of one giant PDF — turned out to be both more reliable to fetch AND more authoritative than the internal policy PDF used for the first pass. If you or a later session need to pull anything else from California, prefer `regulations.justia.com/states/california/title-22/...` over the compiled directives PDF for exactly this reason. The same pattern held for Texas: `regulations.justia.com/states/texas/title-26/...` (small per-section pages) was far more reliable than the large compiled minimum-standards PDF.

**Confidence levels, concretely:**
- Highest confidence: anything marked "CONFIRMED current" or backed by two-plus independent, unrelated sources agreeing word-for-word (the federal 180-day rule, the Texas Title 26 renumbering, the California capacity/sibling exception chain — each cross-checked across 2-3 independent mirrors).
- Medium confidence: entries from a single source that fetched cleanly and consistently, with a specific page/section citation.
- Lower confidence, flagged individually: the Texas training-hours table (came from a graphic the fetch tool read for me, not independently visually confirmed), a few Texas citations not re-verified against current numbering this round (marked "spot-check before use" in their own citation text), and the federal citations sourced only from a state's cover letter rather than the ICPC regulation text directly (though the 180-day figure specifically was independently corroborated a second way).

**Nothing here should be treated as legally verified.** `verified: false` is set on every single entry deliberately. The citations are real and specific enough to check quickly — that was the point of doing it this way — but "AI read the actual regulation and quoted it accurately" is still one step short of "a person confirmed it."

## What changed in this final session, and why

Three research rounds produced 72 requirements (35 original California + 12 California capacity/physical-environment + 20 Texas + 5 federal) plus a documents stub list, all delivered to Christopher already. This session did the remaining preparation work before handoff, across two rounds of its own — the first closing the California sending-side gap, the second (after Christopher decided the demo should cover both directions) closing the matching Texas sending-side gap:

**1. Fact-naming reconciliation.** The 72 requirements had accumulated three different naming styles for the same kind of thing — dot-namespaced (`fact.person.legal_name`, the style the project's own Step 2 design called for), hyphenated conditions (`fact-no-1522g-disqualifying-conviction`), and bare snake_case (`applicant_age`). All 26 non-canonical references across the four requirement files were mechanically renamed to the dot-namespaced style, with a full old-name → new-name mapping (see the git commit / diff, or ask this session's transcript). Two additional issues were fixed during this pass, not just renamed:
   - Two facts had a numeric threshold baked into the name itself (`general_training_hours_ge_8`, `normalcy_training_hours_ge_2`). Renamed to `fact.training.general_hours_completed` / `fact.training.normalcy_hours_completed` — the raw measured value is the fact; the `>= 8` comparison belongs in whatever rule checks it, not in the fact's identity. Mixing the two would mean re-deriving a new fact type every time a threshold changes.
   - Several facts that sound like simple booleans are actually legal or professional judgment calls, not things a vision model should ever assert directly: `fact.criminal_history.has_qualifying_conviction_or_arrest` and `fact.criminal_history.no_1522g_disqualifying_conviction` need to be **derived** by code comparing an extracted list of offense codes against two *different* statutory offense lists (Health & Safety Code §1522(e) vs. §1522(g)(1)(A)-(C) — these are not the same list, one is a documentation trigger, the other is an absolute bar, and conflating them would be a real correctness bug). Similarly, `fact.household.spouse_unsupervised_access_determination` and `fact.capacity.agency_determination_home_can_meet_needs` are explicitly framed in the source text as an agency's own judgment call — these are marked `source: attested`, meaning a caseworker enters them, and must never be computed or inferred by the engine. This distinction (extracted vs. attested vs. derived) is now a field on every entry in the registry — see below.

**2. Step 2 deliverable: `shared/fact-types.json`.** The full registry, every fact from every requirement file, in the reconciled naming, each tagged with `value_type`, and a `source` of `extracted` / `attested` / `derived` with a one-line reason where it's not obvious. Two open items are flagged inside the file itself: the offense-code list itself isn't yet a registered fact type, and the actual HSC §1522(e)/(g) offense codes haven't been transcribed into a reference data file — both are needed before the criminal-history derivation logic in `consistency.ts` can actually run.

**3. `shared/dependency-sequencing-worksheet.md`.** Rather than mechanically forcing `depends_on` edges onto all 72 requirements to make the graph look deep, this groups every requirement into its natural life-cycle phase (intake → background screening → home/physical environment → psychosocial → health/training → filing/decision), based on what the source citations actually establish. Two new edges were added directly, because the source text made them near-explicit rather than inferred. Everything else is left as a short, structured decision for a human (or Claude Code, with a human confirming) to wire — see the worksheet for the reasoning on each phase boundary.

**4. California sending-side — the first direction gap, caught by Christopher.** Every requirement through round 3 was `direction: "receiving"` for both states. Christopher pointed out that the actual demo is California **sending** a child to Texas **receiving** — meaning the 47 California requirements above apply to the *wrong* direction for a CA→TX demo (they're what California would require if California were receiving from Texas), while the 20 Texas requirements are correctly usable as-is, since Texas *is* receiving in that direction.

   To fix this, this session researched and added `ca/requirements/draft-sending-side.json` — 10 requirements covering what a California caseworker must do to send a child to another state: court authorization, ICPC packet compilation (case plan, court report, SSN card, birth certificate, medical/dental/educational/mental-health records), the Financial/Medical Plan, ICPC-100A generation and forwarding, the 100B on placement, and post-placement supervision. Sourced primarily from LA County DCFS Policy 0100-525.10 (a **county**-level policy, not a statewide CDSS regulation — California administers child welfare at the county level, so treat the county-specific items, especially the 3-day/5-day timelines and the DCFS 710/711/712 form numbers, as illustrative rather than binding statewide) with one item — the Financial/Medical Plan — independently corroborated at the statewide level by CDSS ACIN I-95-06, which is why that one entry carries higher confidence than the rest of the file. Each entry's `source_citation` says explicitly which level (county vs. state) it comes from.

**5. Texas sending-side — the demo expanded to cover both directions, so this gap had to close too.** Christopher then decided the demo should show both CA→TX and TX→CA. That meant Texas needed its own sending-side ruleset, the mirror image of item 4. This session added `tx/requirements/draft-sending-side.json` — 13 requirements, sourced from the **DFPS Child Protective Services Handbook, Chapter 4500 ("Interstate Placements")**, corroborated by the statewide DFPS ICPC Resource Guide. This is a *stronger* source than California's: Chapter 4500 is Texas's own official, statewide casework policy (not a county manual), with real named timelines throughout (a 15-calendar-day submission deadline, a 30-calendar-day TICO deadline, a 3-business-day expedited submission deadline, a 3-business-day/2-business-day/2-business-day/24-hour internal routing chain for the 100B, a 6-month approval validity window). It also surfaced a genuine relative-specific rule worth knowing about: Texas has an **expedited ICPC pathway** (Section 4512) available only for specific relationships (parent, stepparent, grandparent, adult sibling, adult aunt/uncle, guardian — explicitly NOT cousins, great-aunts/uncles, or fictive kin) combined with a qualifying circumstance (sudden incarceration/incapacitation/death of a parent, an existing emergency placement, a court-found sibling bond, or the child being 4 or younger). That eligibility test isn't fully formalized into checkable logic yet — see the open item added to `fact-types.json` — but the pathway itself, and its 3-day filing deadline instead of 15, is real and cited.

   Two document ids that were originally California-specific (`doc-ca-child-ssn-card`, `doc-ca-child-birth-certificate`, `doc-ca-monthly-contact-log`) were generalized to `doc-child-ssn-card`, `doc-child-birth-certificate`, and `doc-monthly-contact-log` this round, since Texas's sending-side packet needs the literal same documents and inventing a near-duplicate TX-prefixed id for them would have been worse than reusing the real shared concept. Everything else new is state-specific and kept separate on purpose — see the reconciliation notes inside `documents/draft-documents.json` for the reasoning on each one.

   Deliberately **not** modeled in the Texas sending-side file: the non-custodial-parent placement pathway (Chapter 4500, Section 4513, which can legally skip a full ICPC home study if parental rights were never terminated — a real but procedurally distinct track from kinship placement) and the disaster-relocation chapter (9000/9500 series). Both are flagged in a trailing note inside `draft-sending-side.json` (TX) rather than silently dropped.

   **Both directions are now fully covered.** `shared/demo-direction-map.md` (new this round) is the exact requirement-id manifest for each direction — CA→TX uses California-sending + Texas-receiving + federal (35 requirements total), TX→CA uses Texas-sending + California-receiving + federal (65 requirements total) — so Claude Code doesn't need to re-derive the split from each file's `state`/`direction` fields by hand. It also documents the corpus-wide validation that was run after this file was added: no duplicate requirement ids across all 95 requirements, no `depends_on` edge pointing to a nonexistent id, no dependency cycles, and no dangling `satisfied_by_documents`/`satisfied_by_facts` reference — re-run that check (a short Python script, not hard to reproduce) after any further edits to catch regressions early.
